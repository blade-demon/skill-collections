# Authoring a New Sample

> How to go from "I have a UI unit I want to demonstrate" to a complete `samples/<skill-name>/<sample-name>/` directory that other people can read, run, and learn from.

This guide assumes you've read [`repo-workflow.md`](./repo-workflow.md) and understand the difference between **golden regression samples** (for example `skills/design-to-spec/examples/`) and **hands-on samples** (for example `samples/design-to-spec/search-panel/`). This guide is only about the latter.

---

## 1. Decide whether a new sample is warranted

Before adding `samples/<skill-name>/<sample-name>/`, answer:

- **Is it a different shape from existing samples?** Existing: `search-panel` (input + submit + result list). A new sample is justified if it exercises something the existing ones do not, e.g.:
  - Different binding direction emphasis (props-only, ui_to_event-heavy, ui_to_api-heavy)
  - Different API shape (multi-endpoint with dependencies, paginated, polled)
  - Different UI pattern (form, table, wizard, dashboard)
- **Will it teach something new?** If readers would learn the same lesson from an existing sample, don't add another. Update the existing sample's `walkthrough.md` instead.
- **Will you actually maintain it?** Each sample is a small project that drifts as deps update. Don't ship samples you won't keep green.

Reject reasons (don't ship the sample):

- "I want to demonstrate scenario X" but X is just `search-panel` with different content
- "It would be cool to show off framework Y" without a concrete teaching goal
- A speculative sample for "future" use cases

---

## 2. Directory contract

Every sample has exactly this structure:

```
samples/<skill-name>/<sample-name>/
├── README.md           # 1-page: what's the goal, what does it teach, how to run
├── package.json        # Workspace member; declare deps, build/lint scripts
├── inputs/             # Raw materials (immutable once committed)
│   ├── design.svg      # Or design.png — the visual
│   ├── api.md          # Or api.yaml / api.ts — interface description
│   └── interaction-notes.md  # Plain-language interaction description
├── design-spec/<unit>/ # Generated by design-to-spec skill
│   ├── contracts/
│   │   ├── ui-schema.yaml
│   │   ├── api-schema.yaml
│   │   └── mapping-logic.yaml
│   ├── notes.md
│   ├── data-fetching.md
│   └── specs/<cap>/spec.md
├── src/                # Implementation that consumes design-spec/, never inputs/ directly
│   ├── index.html
│   ├── main.js (or main.ts)
│   └── style.css
└── walkthrough.md      # Process narrative, ≤ 200 lines
```

**Rules**:

- `inputs/` is immutable after the sample lands. If you need to evolve, fork the sample (e.g. `search-panel-v2`).
- `design-spec/` is the skill's output. Regenerate it whenever contracts change; commit the result.
- `src/` consumes `design-spec/` only. Not `inputs/` directly. This enforces the skill's value proposition: _spec is the contract_.
- `walkthrough.md` records what happened during sample creation. Future readers learn from it.

---

## 3. Authoring sequence

```
1. Pick name (kebab-case, no numerical prefix)
2. Author inputs/ (this is where most of the human thinking goes)
3. Run the design-to-spec skill on inputs/
4. Save the output to design-spec/<unit>/
5. Validate: run validate-contracts.js + validate-output.js --strict
6. Implement src/ from design-spec/
7. Verify the implementation against spec.md Scenarios manually
8. Write walkthrough.md retrospectively
9. Add a regression test if the sample exposes a skill-level invariant
```

Don't skip step 5. Don't write `src/` before `design-spec/` is final.

---

## 4. Authoring `inputs/`

This is where most reader value comes from. Specifically:

### `design.svg` (or `design.png`)

- Show **all states** in one image (success / loading / empty / error / partial / disabled — whichever apply).
- Use the same visual style as `skills/design-to-spec/examples/today-windvane/input.svg` for consistency:
  - Background `#F4F5F7`
  - Card background `#FFFFFF`, stroke `#E5E6EB`, `rx="12"`
  - Primary text `#1D2129`, secondary `#86909C`
  - Highlight `#F53F3F`, accent `#FF7D00`, link `#1664FF`
  - Font: `-apple-system, BlinkMacSystemFont, 'PingFang SC', sans-serif`
- Comment the SVG header with intent:

  ```xml
  <!--
    <SampleName> 示例输入 mockup —— <一句话说明>。
    完全虚构，零版权风险。
  -->
  ```

### `api.md`

- Markdown describing the relevant endpoints. Keep it small: only the endpoints `<unit>` actually consumes.
- For each endpoint, document: URL, method, params (with types and required-ness), response fields (with types, nullability, enums in full), error shape.
- If there is no API (props-only sample), still create `api.md` with a one-paragraph explanation: "This is a props-only component. Data is provided by the parent via props ..."

### `interaction-notes.md`

- 5–15 sentences. Plain language, no markdown formality.
- Cover: what triggers the request, what success looks like, how empty differs from error, any debounce/abort/cache concerns, any cross-component coupling.
- Bullet points are fine. Don't over-structure.

This is what gets pasted into the skill's stage three.

## 5. Running the skill

After `inputs/` is ready:

```bash
# From the repo root
cd samples/design-to-spec/<sample-name>

# (Manually walk through the four-stage skill flow with an LLM session.
#  See skills/design-to-spec/ONBOARDING.md §7 for the command form.)

# After the LLM has written contracts/*.yaml, generate the markdown:
node ../../../skills/design-to-spec/scripts/generate-output.js \
  --ui design-spec/<unit>/contracts/ui-schema.yaml \
  --api design-spec/<unit>/contracts/api-schema.yaml \
  --mapping design-spec/<unit>/contracts/mapping-logic.yaml \
  --out-dir design-spec/<unit>

# Validate
node ../../../skills/design-to-spec/scripts/validate-contracts.js \
  --ui design-spec/<unit>/contracts/ui-schema.yaml \
  --api design-spec/<unit>/contracts/api-schema.yaml \
  --mapping design-spec/<unit>/contracts/mapping-logic.yaml

node ../../../skills/design-to-spec/scripts/validate-output.js --strict \
  --ui design-spec/<unit>/contracts/ui-schema.yaml \
  --api design-spec/<unit>/contracts/api-schema.yaml \
  --mapping design-spec/<unit>/contracts/mapping-logic.yaml \
  --notes design-spec/<unit>/notes.md \
  --data-fetching design-spec/<unit>/data-fetching.md \
  --spec design-spec/<unit>/specs/<cap>/spec.md
```

Both validators must exit 0 before you commit.

## 6. Writing `walkthrough.md`

Aim for ≤ 200 lines, written **after** the sample is complete. Cover:

- **Stage 1 (visual extraction)**: which components were obvious, which were `inferred`, which were `needs_human_input`. What the ASCII tree summary looked like.
- **Stage 2 (API extraction)**: which fields the skill kept vs filtered. Any enum surprises. Any `[UNKNOWN]` markers and why.
- **Stage 3 (logic mapping)**: which interactions were captured. Any state machine transitions you nearly missed. Any `mapping.open_questions` you registered.
- **Stage 4 (generation)**: which markdown sections looked good, which needed manual polish, which `open_questions` made it to the final summary.

Format suggestion:

```markdown
# Walkthrough: <SampleName>

> How this sample's `design-spec/` was generated from `inputs/`.

## Stage 1 — Visual extraction (WAITING_FOR_UI)

What I uploaded: <description of inputs/design.svg>

Skill output (abbreviated):

\`\`\`text
<the ASCII tree the skill returned>
\`\`\`

Notes / surprises:

- ...

## Stage 2 — API extraction (WAITING_FOR_API)

...

## Stage 3 — Logic mapping (WAITING_FOR_MAPPING)

...

## Stage 4 — Generation (GENERATING_SPEC)

...

## Open questions that remain

- [P0] ...
- [P1] ...
```

If the sample exposes a real skill-level gap (like `price-card` did with the missing `props_to_ui` direction), highlight it in walkthrough.md and add it to `skills/design-to-spec/references/future-tracking-stage.md` or open an issue.

## 7. Implementing `src/`

Rules:

- **Read only `design-spec/`**, never `inputs/`. The implementer is supposed to be a different person from the spec author. If you need information that's only in `inputs/`, that's a sign the spec is incomplete — go fix the contract.
- Match the spec's `state_machine` literally. Each transition in `mapping-logic.yaml` should be a code path in your implementation.
- Match `bindings` literally. `ui_to_api` bindings become request payload assembly; `api_to_ui` become render bindings; `ui_to_event` become event emitters.
- Implement Scenarios from `spec.md` as test cases (manual verification is fine for samples; automated is better when easy).

Tooling choice for `src/`:

- Default to **vanilla HTML + JS + CSS** unless the sample specifically demonstrates a framework feature. Vanilla is lowest-friction for readers.
- If you need a build tool, prefer **Vite** (single dep, sensible defaults) over webpack/rollup.
- No TypeScript by default. Add it only if the sample teaches type-related patterns.

---

## 8. Sample-level test (optional)

If your sample exposes a skill-level invariant worth pinning, add a test under `skills/design-to-spec/scripts/tests/`. Pattern: see `skills/design-to-spec/scripts/tests/price-card.test.js`.

Don't add per-sample tests for the implementation itself unless the sample is specifically about testing patterns.

---

## 9. PR checklist

Before opening a PR for a new sample:

- [ ] `inputs/` is committed and self-contained (no external links, no proprietary assets)
- [ ] `design-spec/` exists and validates clean
- [ ] `src/` builds (if it has a build) and runs locally
- [ ] `walkthrough.md` is written and ≤ 200 lines
- [ ] `samples/<skill-name>/<sample-name>/README.md` explains the goal in 1 paragraph
- [ ] Top-level `npm run check` passes
- [ ] Either added a regression test or documented why none was needed
- [ ] No proprietary content, no copyrighted images, no real customer data

---

## 10. Anti-patterns

- ❌ Skipping `inputs/` and writing `design-spec/` directly. (Bypasses the skill, which defeats the sample's purpose.)
- ❌ Updating `inputs/` after `design-spec/` was generated. (Now the spec doesn't match the inputs anymore.)
- ❌ Reading `inputs/` from `src/`. (Bypasses the spec contract.)
- ❌ Adding 5 samples that are all the same shape. (One sample is enough; cover different shapes.)
- ❌ Numerical prefixes on directory names (`01-`, `02-`). (Implies an order that doesn't exist; rename hell when adding mid-sequence.)
- ❌ Generated artifacts (node_modules, dist) committed. (Use `.gitignore`.)
- ❌ Nested `.git/` directory. (If you brought a sample from another repo, remove its `.git`.)
