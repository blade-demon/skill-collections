# 置信度与证据纪律细则

> 判断「这条结论能不能写成事实」时读本文。核心目标：**防止幻觉在文档链路里累积成「看起来权威的错误」**，因为目标读者是不熟悉项目的新人，他们会照着文档当真。

## 一句话纪律

> 能被代码验证的才是事实；只能被命名/结构暗示的是推测；连暗示都不足的是待确认。**宁可少写，不要写错。**

## 置信度三档

| 置信度 | 判据（满足任一）                                                                                                       | 文档里的写法                     |
| ------ | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| 高     | ① 有直接的代码调用链；② 有注解/装饰器明示（`@GetMapping`、路由配置）；③ 有配置文件支持；④ 有测试覆盖；⑤ 有类型定义约束 | 直接陈述为事实                   |
| 中     | 只能靠命名约定、目录结构、调用关系**合理推断**，无直接证据                                                             | 必须带「（推测）」               |
| 低     | 代码证据不足，或涉及运行时动态行为、外部系统、反射/AOP 织入，静态无法确认                                              | **禁止进正文**，只进「待确认项」 |

## 常见「会骗人」的场景，默认降一档

- **命名很像但没调用**：`OrderServiceImpl` 存在 ≠ 它被用。要看有没有被注入/调用。
- **接口存在但可能废弃**：有 Controller ≠ 前端在用。P4 反查没找到调用方时标「未发现前端调用」，不要假设它活跃。
- **AOP / 拦截器 / 注解处理器**：鉴权、事务、日志常通过切面织入，源码线性读不到。涉及时标「中/待确认」，别断言执行顺序。
- **动态 URL / 反射 / SpEL**：`@RequestMapping("${...}")`、模板字符串拼 URL → 静态无法确定，标「待确认」。
- **外部系统**：FeignClient / RestTemplate 指向的远端逻辑不在本仓 → 只能描述「调用了什么」，不能描述「对面做了什么」。
- **配置随环境变化**：baseURL、开关、profile 在运行时注入 → 写明「随环境，见 `<配置文件>`」，不要钉死一个值。

## 证据怎么记才算数

一条够格的证据 = **路径 + 行号 + 一句「它凭什么成立」**。

- ✅ 好：`OrderController.java:34` 类级 `@RequestMapping("/api/orders")` + 方法 `@GetMapping` → 确认 `GET /api/orders`
- ❌ 不够：「订单接口在 OrderController 里」（无行号、无凭据，无法复核）

## 与文档的联动（P7/P8 强制）

1. 高置信度 → 可写成事实；P8 用 Grep/Glob 抽查路径与符号真实存在。
2. 中置信度 → 文档里出现时必须带「（推测）」；P8 检查措辞没有偷偷去掉标注。
3. 低置信度 → 不进正文；P8 反查正文里若出现该结论即判「不通过」，打回降级。

## 取舍原则

新人文档的价值在**可信**。一条标着「待确认」的真问题，比一条编圆了的假闭环有用得多。遇事不决，降一档。
