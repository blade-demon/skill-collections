# Phase 8 — Evidence-Based Validation 模板

> 草稿先落 `docs/.analysis/08-validation-report-draft.md`，定稿写 `docs/validation-report.md`。
> 对 P7 生成的最终文档做强校验。逐项核对——**能用工具核对的就核对**（脚本查 Mermaid/路径/Evidence，Glob 查路径，Grep 查符号），不要凭印象判过。
> 每个校验项按 `schemas/validation-record.md` 记录。发现问题按「失败处理规则」修正文档或降级结论，并回写。
> **工具核对本身也要自检**：发现「路径/符号缺失」时，先排除是不是校验命令的误差再判失败——常见陷阱：① `rg -o` 多文件时会前缀文件名（用 `--no-filename`）；② 正则 `js` 会抢先匹配 `.json`（把更长扩展名放前面或加词界 `\b`）；③ `class User` 会子串命中 `UserContext`（用 `@Entity` / 词界精确匹配）。先复核命令，再下「不通过」结论。
> **本阶段暂不执行目标项目的构建、测试、lint、typecheck 命令。** P8 只校验静态文档、Mermaid 与代码证据。

## 步骤 0：先跑确定性脚本

人工过 checklist 前，先运行确定性脚本批量核对路径、符号、Mermaid 结构/数量、图级 Evidence，以及 `index.json` 的结构/路径/Evidence/引用完整性：

```bash
node skills/react-spring-project-doc/scripts/validate-docs.js \
  --project <目标项目根> --symbols --strict
# 退出码 0 = 全部通过；1 = 有缺失路径/符号、Mermaid 结构错误、Evidence 未定位或 index.json 校验错误
```

把脚本输出映射到 checklist：缺失路径对应 V-001；符号问题对应 V-002；Mermaid 结构、数量或 Evidence 声明失败对应 V-003；`index.json` 校验错误对应 V-014。API 映射、链路闭环、图中每条边的业务真实性和文档矛盾仍需人工逐项核对。脚本若提示「未发现 docs/index.json」，说明 P7 漏生成,回 P7 补。

> 符号告警分两档，处理方式不同：
>
> - **「符号在代码里完全未出现」**（`absent`）：疑似幻觉符号，按 V-002 删除确定结论或移入待确认；`--strict` 下视为硬失败。
> - **「符号被引用但未见定义」**（`referenced`）：多为框架/外部类型（如 `ResponseEntity`）或注释里的提及，脚本只告警、不硬失败。逐条人工确认——若确为本仓应有的类却查不到定义，按 V-002 处理；若是框架/外部类型则照常引用即可。

## 失败处理规则

1. **文件路径不存在** → 修正文档，或移入「待确认项」。
2. **符号不存在** → 删除确定结论，或移入「待确认项」。
3. **API 映射失败** → 标注「未匹配」，不得写成完整链路。
4. **业务链路不闭环** → 标注「部分完整」或「待确认」。
5. **结论无证据** → 降级为「推测」或「待确认」。
6. **文档矛盾** → 修正后在证据账本重新记录。
7. **Mermaid 结构或 Evidence 声明失败** → 修正 fence、图数量、声明或引用。
8. **Mermaid 节点/连线无证据** → 删除节点/连线，或改成「断点：待确认」。
9. **图把不完整链路画成闭环** → 按 P5 完整性结论截断，不得视觉补全。
10. **index.json 校验错误** → 按错误类型修正：路径/符号不存在同 V-001/V-002；`E-xxx` 不在账本或引用不闭合 → 对齐证据账本；`usedByApi`/`usedByFlow` 悬挂 → 修正为真实 id。
