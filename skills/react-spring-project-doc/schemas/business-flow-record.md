# Business Flow Record 格式

`docs/.analysis/05-business-flows-draft.md` 里每条业务链路的字段定义。

## 链路标识

- 编号：`F-1`、`F-2`…（全局唯一）。
- 名称：用业务语言命名（「用户下单」「订单列表加载」），不要用技术名。

## 环节字段（每条链路必填）

| 环节                 | 必须包含                   | 缺失时               |
| -------------------- | -------------------------- | -------------------- |
| 用户入口             | 用户从哪触发               | 写「待确认」         |
| 前端路由             | 路由路径                   | 写「待确认」         |
| 前端页面组件         | 组件名 + path              | 写「待确认」         |
| 触发事件             | 事件处理函数 + path:line   | 写「待确认」         |
| 前端 API 方法        | 方法名 + path:line         | 链路降级为「不完整」 |
| HTTP 方法 + URL      | 方法 + 拼接后 URL          | 链路降级             |
| 请求参数             | 关键字段名:类型            | 标「待确认」         |
| 后端 Controller 方法 | `Class.method` + path:line | 链路降级             |
| 后端 Service 方法    | `Class.method` + path:line | 标「待确认」         |
| 数据访问方法         | `Class.method` + path:line | 标「待确认」         |
| 涉及数据模型         | 模型名 + path              | 标「待确认」         |
| 返回数据             | 返回结构关键字段           | 标「待确认」         |
| 前端如何渲染返回     | 渲染行为 + path:line       | 标「待确认」         |
| 异常路径             | 至少 1 条失败分支表现      | 标「待确认」         |

> 每个环节尽量带 `path:line` 证据。带证据的环节才算「确定」。

## 完整性判断（必填）

| 取值         | 判据                                           |
| ------------ | ---------------------------------------------- |
| `完整`       | 从用户入口到数据访问每一环都有代码证据串通     |
| `部分完整`   | 主干通，但个别环节靠推断（命名/约定）          |
| `不完整`     | 存在断点，关键环节找不到证据                   |
| `需人工确认` | 涉及动态分发、运行时注入、跨服务，静态无法确认 |

## 配套

- 每条链路在证据账本登记一条 Evidence（类型：业务链路），置信度对应完整性判断。
- 「不完整 / 需人工确认」的链路，**进最终文档时必须保留该标注**，不得补全成闭环。
