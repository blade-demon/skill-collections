# 案例研究：feedback-form — 用 vs 不用 design-to-spec 的差异

> 这不是性能 benchmark，是**同一个真实需求**用两种工作流跑下来的对比。所有"工作量估算"基于一名熟练前端工程师，假设需求评审已开过、设计稿已交付。

> 原始物料和产物在 [`samples/design-to-spec/feedback-form/`](../../../samples/design-to-spec/feedback-form)；过程记录在 [`samples/design-to-spec/feedback-form/walkthrough.md`](../../../samples/design-to-spec/feedback-form/walkthrough.md)。本文档关注**工作量分布**而非过程细节。

---

## 0. 需求长什么样

一个反馈表单组件：

- 3 个表单字段：`rating`（5 颗星，必填）、`comment`（多行输入，必填，1–500 字）、`email`（可选，需邮箱格式）
- POST `/api/v1/feedback` 提交，返回 `feedback_id` + `submitted_at`
- 业务异常 5 种：成功 / 字段校验失败 / 限流 / 网络错误 / 鉴权失败
- 双层校验：前端阻塞性校验 + 后端 `VALIDATION_FAILED` 返回 `data.field_errors`
- 提交期间所有字段 disabled；成功后整个表单替换为感谢页（不是叠加 toast）
- 限流后按钮 30 秒倒计时禁用

设计稿：4 张图（idle / submitting / success / error）。
接口文档：1 份 markdown，约 80 行。

## 1. 不用 design-to-spec — 传统工作流

### 1.1 时间线

| 阶段     | 工作                                                                      | 估时        |
| -------- | ------------------------------------------------------------------------- | ----------- |
| 评审会前 | 自己读设计稿 + 接口文档；把疑问写进飞书评论                               | 0.5h        |
| 评审会   | 与 PM / 后端 / 设计 / QA 拉会，过设计稿和接口                             | 1h          |
| 评审会后 | 整理会议记录，转发给相关人                                                | 0.5h        |
| 实现     | 写 form / 状态机 / 校验 / 错误处理 / submit 流                            | 4–6h        |
| 联调     | 与后端对错误码、字段名、限流响应；改 1–2 轮                               | 1.5h        |
| 测试     | QA 写用例时回头问"empty 态什么样"、"rateLimit 视觉"、"email 可选时怎么传" | 0.5–1h      |
| 埋点补   | 上线前一天数据团队来要求加 4 个事件，覆盖原代码的 onClick / onSubmit      | 1h          |
| 修复回归 | 埋点改动破坏了原本能跑的 form clear 逻辑                                  | 0.5h        |
| **小计** |                                                                           | **9.5–12h** |

### 1.2 实际会漂移的事项（90% 项目都会发生 ≥ 2 个）

1. **评审"达成共识"但没沉淀**：评审会上口头同意「rate-limited 显示按钮内倒计时」，会后没人写进文档；前端实现时凭记忆写成"灰按钮+ 全局 toast"，与 PM 期望不一致 → 上线前一天发现，回炉。
2. **错误码不全**：接口文档列了 4 类 code，实际后端返回 `RATE_LIMITED` 但文档漏写；前端没兜底，上线后偶现"提交失败但无提示"。
3. **`email` 可选时怎么传**：前端实现凭直觉写了 "空字符串也提交"，后端校验失败；联调时才对齐为 "空就省略字段"。
4. **限流倒计时视觉**：设计稿没给具体样式（按钮上数字 vs 进度条），前端硬猜了一个，PM 上线后说不对。
5. **埋点漏覆盖**：rate-limit 触发没埋点，数据团队事后看不到限流频率。
6. **field-level invalid 状态语义错乱**：邮箱格式错了导致整个 form 进 error 态 → 用户输入框红框但 comment 也变红，体验奇怪。

### 1.3 上述漂移的真实代价

| 漂移项                 | 平均代价                               |
| ---------------------- | -------------------------------------- |
| 上线前一天发现需要回炉 | 0.5 工作日（同步沟通 + 改代码 + 重测） |
| 联调多 1 轮            | 1–2 小时 + 后端工时                    |
| 上线后埋点回补         | 0.5 工作日（含发布流程）               |
| 状态语义返工           | 1–3 小时                               |

合计：**额外 4–8 工时**散落在多个时间节点，且每次都让心智重新切回这个组件。

## 2. 用 design-to-spec — 新工作流

### 2.1 时间线

| 阶段     | 工作                                                                                                                | 估时           |
| -------- | ------------------------------------------------------------------------------------------------------------------- | -------------- |
| 跑 skill | 4 阶段对话：上传设计稿 + 接口 + 描述交互；每阶段确认                                                                | 0.5–1h         |
| 自动产出 | `contracts/*.yaml` + `notes.md` + `data-fetching.md` + `spec.md` 写盘                                               | 0（脚本秒级）  |
| 评审会   | 拉会，但每人**只看自己角色对应的产物**（见 [reviewer-guide.md](../references/reviewer-guide.md)）；P0 / P1 当场认领 | 0.5h           |
| 评审后   | 改 contracts → 重跑 generator；不再"会议纪要分发"                                                                   | 0.25h          |
| 实现     | 按 `data-fetching.md` 状态机 + `spec.md` Scenario 写代码                                                            | 3–4h           |
| 联调     | 错误码、字段名都在 `api-schema.yaml` 里写死了，后端拿同一份；几乎不需要回头扯皮                                     | 0.25h          |
| 测试     | QA 直接拿 spec.md 的 Scenario 写用例，每个枚举值都已展开                                                            | 0（QA 自己跑） |
| 埋点     | `notes.md §埋点锚点` 表已列出所有事件名；上线前数据团队 review 即可                                                 | 0.25h          |
| **小计** |                                                                                                                     | **4.75–6.25h** |

### 2.2 漂移被前移到了哪一步

每个原本会"上线前才暴露"的问题都在跑 skill 时被**显式登记**：

| 原漂移项                 | 在 skill 里登记成什么                                                                                      | 何时关闭             |
| ------------------------ | ---------------------------------------------------------------------------------------------------------- | -------------------- |
| rate-limited 倒计时视觉  | `mapping-logic.yaml.open_questions.mapping-q1: P1`                                                         | 评审会当场认领设计师 |
| `email` 空怎么传         | 写进 `mapping-logic.yaml.bindings[email].transform: "if empty omit field"`                                 | 阶段三确认时落契约   |
| 错误码不全               | `api-schema.yaml.endpoints[].error_shape.error.code.enums` 当场过一遍                                      | 阶段二接口提纯时     |
| field-level invalid 语义 | `ui-schema.yaml.states.emailInvalid.scope: element + scope_components: [emailField, emailHint]`            | 阶段一视觉提纯时     |
| 埋点缺漏                 | `notes.md §埋点锚点` 表自动从 `ui_to_event` binding 派生                                                   | 评审时               |
| success 是替换还是叠加   | `ui-schema.yaml.states.success.render_assertion: "hides ratingGroup, commentField, emailField, submitBtn"` | 阶段一时             |

`open_questions` 里 P0 一个都没有（feedback-form 的设计稿和接口文档准备质量较高），P1 / P2 共 6 条全部在评审会上当场认领或答复。

### 2.3 时间分布的差异

```
传统工作流（9.5–12h）           design-to-spec 工作流（4.75–6.25h）
│                              │
│ 0.5h 评审前自己读             │ 0.5–1h 跑 skill（一次性投入）
│ 1h 评审会（多人）             │ 0.5h 评审会（角色化、更快）
│ 0.5h 整理会议记录             │ 0.25h 改 contracts 重跑
│ 4–6h 实现                     │ 3–4h 实现（按 spec 直接写）
│ 1.5h 联调（多轮）             │ 0.25h 联调（契约对齐）
│ 0.5–1h 测试时回头问           │ 0   测试自己跑（spec 够用）
│ 1h 埋点回补                   │ 0.25h 埋点 review
│ 0.5h 修复回归                 │
└─                              └─
```

**节省点不在"写代码更快"，在"扯皮更少 + 漂移前移"。** 实际写代码时间只少了 ~30%（4–6h → 3–4h），但联调 / 测试 / 埋点 / 修复加起来从 3.5h 降到 0.75h。

## 3. 这个 case 没有解决的问题

诚实记录，避免过度推销：

- **跑 skill 本身需要 0.5–1h 学习曲线**：第一次用的人可能花 2h（读 ONBOARDING + 试一次）。第二个组件起就稳定。
- **设计稿质量差时收益打折**：如果设计稿只有一张 idle 态、其他状态全靠口头，阶段一 `needs_human_input` 满天飞，仍然要回头补设计——skill 让缺口可见，但不替你补缺口。
- **小型组件 ROI 不高**：< 30 行代码的纯展示组件（如一个 badge），跑 4 阶段反而比直接写代码慢。`examples/price-card/` 是 props-only 退化路径的样例，用 ≤ 15 分钟跑完。
- **跨团队推广有阻力**：后端不愿读 `api-schema.yaml`、QA 不熟 OpenSpec Scenario 时，第一次评审会有摩擦；从第二个组件起阻力消失。

---

## 4. 何时不该用

按 [ONBOARDING.md §2](../ONBOARDING.md) 的口径：

- 纯美学反馈（"这个好看吗"）
- 像素级 CSS 抄写
- < 30 行的纯展示组件（除非你正在把它纳入设计系统）

---

## 5. 一句话总结

> **不是省 50% 编码时间，是把 30% 的扯皮 / 联调 / 回炉时间前移到一次 1 小时的 skill 对话里。**
>
> 真正的复利在第二个组件起：契约 review 节奏稳定、跨角色沟通成本降到几乎为零、上线前不再有"原来那个还没确认"。
